## 0. 30 秒速览

**Karst 是什么**：《红色警戒2：尤里的复仇》的引擎扩展 DLL，通过 Syringe 注入 `gamemd.exe`，
用 hook 改引擎行为。它由**两半**组成，这一点最容易搞错：

| 一半 | 产物 | 语言 | 作用 |
| --- | --- | --- | --- |
| C++ 侧 | `Karst.dll`（263,168 B） | C++ / MSVC x86 | hook 引擎、INI 热重载、按国家外观、加载 C# 宿主 |
| **C# 侧** | **`KarstPatcher\`（22 个 DLL + 2 个 json）** | C# / .NET Framework 4.8 | 运行时用 Roslyn 编译用户写的 `.cs` 脚本并挂到单位上 |

**只复制 `Karst.dll` 等于装了个没有脚本系统的 Karst**，而且失败是静默的（用户的 `.cs` 被忽略）。
这是这份文档最想强调的一件事。

**三件事的做法**：

```powershell
# 1) 构建+校验+部署到测试游戏（C++ 侧）
powershell -ExecutionPolicy Bypass -File Karst\tools\build_deploy.ps1

# 2) 打出完整成品（两半都在里面；产出一个时间戳文件夹，默认不打 zip）
powershell -ExecutionPolicy Bypass -File Karst\tools\package_full.ps1

# 3) 直接部署到某个游戏目录
powershell -ExecutionPolicy Bypass -File Karst\tools\package_full.ps1 -Deploy "E:\_game\RA2\yr_karst_test"
```

清理进 git：`.gitignore` 已经写好并**实测验证**过 —— 705 MB 的工作树，只会提交 **701 个文件 / 6.4 MB**（2026-10-12 实测）。

## 3. 构建：从源码到成品

### 3.1 两条命令分别管什么

```powershell
# C++ 侧：编译 -> hook 校验 -> 部署到测试游戏目录
powershell -ExecutionPolicy Bypass -File Karst\tools\build_deploy.ps1

# C# 侧：编译三层程序集
Karst\refs\DynamicPatcher\build_refs.bat Release
```

`build_deploy.ps1` 有**两道闸门**，都不是形式主义（它们各自救过一次真实崩溃）：

* `tools\hookcheck.py` —— 每个 hook 的 `Size` 必须 ≥5 字节且落在**指令边界**上。
  曾经因为 size 落错位置直接 `0xC0000005`。
* `tools\hookconflict.py` —— 与 Ares / Phobos / Kratos 的 hook 字节不能重叠。
  实测 `0x712040` 与 Ares 的 `0x712045` 相邻，当时游戏一造出建造厂就崩。

任一闸门不过，脚本**拒绝部署**。游戏在跑时也拒绝（DLL 被锁着）。

### 3.2 一键打完整成品

```powershell
powershell -ExecutionPolicy Bypass -File Karst\tools\package_full.ps1
powershell -ExecutionPolicy Bypass -File Karst\tools\package_full.ps1 -NoBuild          # 不重编，只打包
powershell -ExecutionPolicy Bypass -File Karst\tools\package_full.ps1 -Deploy "E:\_game\RA2\yr_karst_test"
```

实测输出：

```
artifact   Karst.dll  263,168 bytes
C# host    KarstPatcher.dll 65,024 bytes
hookcheck  all hooks well formed
hookconflict  no overlaps (3 same-address handler(s) shared, 3 adjacent pair(s) checked)
stage      35 files, 16.7 MB
folder     发布包\2026-10-12-10-10-42\
（文件夹名就是时间戳；默认不打 zip，加 -Zip 才额外产出一个同名 .zip）
```

> ⚠️ **不要用老的 `tools\package.ps1`**。它只打 `Karst.dll`，产出的包里**没有 C# 脚本系统**。
> 证据：`dist\Karst-0.1.0-20261011-0442.zip` 里的 `Karst.dll` 是 112,128 字节，
> 而当前产物是 263,168 字节 —— 那个包早于脚本系统。详见 §5 的待办。

### 3.3 常见构建错误

| 报错 | 原因与处理 |
| --- | --- |
| `MSB3644`（找不到参考程序集） | 缺 **.NET Framework 4.8 目标包**。用 VS Installer → 单个组件装上。**不要**用 NuGet 的 `Microsoft.NETFramework.ReferenceAssemblies` 去绕（实测只能把错误从 73 降到 6，然后卡在隐式 `System.Core 3.5` 上报 CS0433） |
| 首次 `build_refs` 失败 | 需要联网让 NuGet 还原 Roslyn / Newtonsoft |
| `*.ps1` 报语法错误、且错误信息与内容毫不相干 | 文件丢了 **UTF-8 BOM**。Windows PowerShell 5.1 按 ANSI 读 `.ps1`，中文注释会变成乱码。见 §6.4 |
| 执行策略拒绝运行 | 本机策略是 Restricted，所有调用都加 `-ExecutionPolicy Bypass`（`.bat` 包装器已经带了） |

### 4.5 常见故障

| 现象 | 先查 |
| --- | --- |
| 游戏没反应 / 注入失败 | `gamemd.exe` 与 `Syringe.exe` 必须**都以管理员身份**运行。未提权时 Syringe 直接报 `No or invalid command line arguments given` 并退出（与参数写法无关，已对照验证） |
| 脚本被静默忽略 | `KarstPatcher\` 是不是**整个目录**都复制了？少了 Roslyn 那一堆就是这个症状 |
| `BadImageFormatException` | 编译失败会留下 **0 字节 DLL**。宿主已修成"失败即删除"，但如果你手工放进去过坏文件，删掉 `Build\Scripts\` 里的它 |
| 编译报 `error CS0246: 找不到类型 ExtensionReference` | 用户脚本漏了 `using Extension.Utilities;`（最常见的一个坑） |
| 改了 `Scripts=` 没生效 | `rulesmd.ini` 的改动要重开一局 |

### 4.6 一个会静默废掉整个脚本系统的坑：Mark of the Web

**症状**（2026-10-12 换新游戏环境时实测踩到）：

```
karst.log                : ScriptHost: _Assembly::CreateInstance(DynamicPatcher.Program)
                           failed (HRESULT 0x80131604).
KarstPatcher\patcher.log : 根本不存在
syringe.log              : 一堆 Exception (Code: 0xE0434352 ...)   ← CLR 异常
```

**根因链**：

```
文件带 Zone.Identifier 数据流（ZoneId=3，即"来自 Internet"）
  ↓ CLR 拒绝加载（ClrHost 用 _AppDomain::Load_2，受这个标记限制）
_AppDomain::Load_2("KarstPatcher") -> 0x80131515 (COR_E_FILELOAD)
  ↓ Program 的静态构造函数抛异常 -> CreateInstance 返回 0x80131604
  ↓ Patcher.Init 第 77 行的 new FileStream(patcher.log, FileMode.Create)
    在 try 块之外，根本没被执行到
所以：没有 patcher.log，且 karst.log 里只有 HRESULT、没有异常详情
```

**证据**：

| 检查 | 结果 |
| --- | --- |
| 新环境 `KarstPatcher\` 的 24 个文件 | 全部带 `Zone.Identifier`（`ZoneId=3`） |
| 旧环境同目录（能正常工作） | 一个都没有 |
| **打包产物 / 构建输出目录** | 一个都没有 → **包本身是干净的** |
| 用 PowerShell `Assembly.LoadFrom` 复现 | `0x80131515`，与游戏内一致 |

也就是说：**包没问题，是"复制 / 解压到游戏目录"这一步引入的**。
玩家从网盘下载 zip 解压，同样会带上这个标记。

**修复**（已实现，`src\Script\ClrHost.cpp` 的 `UnblockAssemblies`）：
在 `LoadScriptSystem()` 里、CLR 触碰任何程序集之前，删掉 `KarstPatcher\*.dll` 的该数据流：

```cpp
::DeleteFileW((path + L":Zone.Identifier").c_str());
```

删掉的只是 Windows 附加的元数据（不是文件内容），而且只碰我们自己目录下的 DLL。

**验证**（故意制造故障再确认自愈）：手动给 24 个文件全部加上 `ZoneId=3`，然后启动游戏 →

| | 启动前 | 启动后 |
| --- | --- | --- |
| 带标记的文件 | 24 / 24 | **2 / 25**（剩下的正是那两个 `.json`；`UnblockAssemblies` 只处理 `*.dll`，而 json 不由 CLR 加载，无影响） |
| 三个 Karst 程序集的 `LoadFrom` | 全部失败 | **22 个 DLL 全部成功** |
| `patcher.log` | 不存在 | **正常生成**，末尾 `first action complete!`，0 错误 |
| 扩展层 hook | — | `appling AresHook hook: 6F3260, TechnoClass_CTOR, 5` 等，**驱动层已挂上** |

> ⚠️ **给维护者**：如果将来有人把这段 `UnblockAssemblies` 当成"多余的防御"删掉，
> 故障会以完全相同的方式复现，而且**症状极具误导性**（看起来像 config 缺失或 CLR 版本问题）。

## 6. 日常开发

### 6.1 改 C++ 功能

1. 在 `src\Ext\<新功能>\` 新建 `.h/.cpp`，**加入 `Karst.vcxproj`**；
2. 在 `KarstExtension::OnGameStart()` 里 `Ext::<新功能>::Init();`；
3. 新 hook 一律登记在 `src\dllmain.cpp`（保持地址清单可读）；
4. `powershell -ExecutionPolicy Bypass -File Karst\tools\build_deploy.ps1`。

> ⚠️ hook 的 `Size` 必须落在指令边界（`tools\disrva.py <exe> <addr> <n>` 可核对）。
> 另外：构造/析构期不要读对象字段，回调用户代码要逐个隔离异常。

### 6.2 改 C# 侧

编辑 `refs\DynamicPatcher\` 下源码 → `build_refs.bat Release`。
改动请继续用 `// KARST ADDITION:` / `// KARST FIX:` 标注并写上原因。

### 6.3 给脚本工作室加积木

积木库是 `tools\script-studio\blocks\*.js`，加积木只需在 `registry.js` 里加一个定义
（`needs` / `args` / `events` / `emit`），然后：

```powershell
powershell -ExecutionPolicy Bypass -File Karst\tools\script-studio\build_studio.ps1
node Karst\tools\script-studio\tests\run_tests.js --compile     # 自动为新积木生成夹具并编译
node Karst\tools\script-studio\tests\check_page.js
```

**测试是自动覆盖新积木的**：每个积木 × 每个合法事件都会生成一个 `.cs`，用与游戏内
**同参数**的编译器编一遍。所以"这个积木能不能编译"不需要靠人去游戏里试。
（实测：92 个夹具 92 ok / 0 error；`verify_compile.ps1` 与游戏内编译同一文件产出字节数一致。）

### 6.4 ⚠️ 两个会反复踩的编码/路径坑

1. **含中文的 `.ps1` 必须存成 UTF-8 with BOM。** PowerShell 5.1 按 ANSI 读 `.ps1`，
   丢 BOM 后中文变乱码，报出的语法错误与真实原因毫无关系
   （例如 `The '<' operator is reserved for future use`）。本仓库里带 BOM 的：
   `build_editor.ps1`、`build_studio.ps1`、`package_full.ps1`。
   `verify_compile.ps1` 是纯 ASCII，不受影响。
2. **`-File` 传数组参数时逗号不是分隔符**：`-Path a.cs,b.cs` 会当成一个路径。
   `verify_compile.ps1` 因此自己按 `,`/`;` 拆分。

改 `rulesmd.ini` 的正确姿势（**已实测**）：定位目标小节的字节区间，只在区间末尾**插入**，

> （31,061 个 `\r\n`、**0** 个裸 `\n`）。行尾统计会随文件被替换而变化，所以每次动手前
> 都按上面的字节区间法现场测一遍，不要沿用旧数字（做法本身不变）。
