## Karst 使用说明

> 本文档说明 Karst 当前提供的功能与配置方法。
> 相关技术细节与逆向结论见源码仓库的 `docs\二次开发须知.md`。

---

## 一、ShowByArt —— 让建筑显示成另一个建筑的样子

### 它做什么

在建筑的配置段里写一行，这个建筑就会**完全使用另一个建筑的 ART**：

| 跟随的内容 | 说明 |
| --- | --- |
| 主体图像 | 目标建筑的外观 |
| **全部动画** | 待机、生产、破损、**活动件（`_a`）**等，全部由引擎自己创建 |
| 占地大小 | 目标建筑的 `Foundation`（外观变了占地也跟着变） |
| 色盘与偏移 | 引擎自己的，与原版完全一致 |

**Karst 不做任何绘制**：它只是在引擎读取 ART **之前**把段名改掉，
之后的一切（建图像、建动画、定位、上色）都由引擎按它自己的规则完成。

### 配置方法

写在**被改变的那个建筑**自己的段里：

```ini
; 苏军电厂显示成盟军电厂
[NAPOWR]
ShowByArt=GAPOWR
```

位置：`rulesmd.ini`（优先）或 `artmd.ini`（次之），两者都支持。

### 两个键

| 键 | 必需 | 含义 |
| --- | --- | --- |
| `ShowByArt` | ✅ | 要模仿的建筑的 **ART 段名** |
| `ShowByArtType` | 可选 | 该建筑在引擎里的**类型 ID**，**仅当它与段名不同时**才需要 |

别名（大小写不敏感）：

- `ShowByArt` = `art.show_by_art` = `ShowBySHPName` = `ShowByBuilding`
- `ShowByArtType` = `art.show_by_art_type`

### 什么时候必须写 ShowByArtType

**当目标建筑的 `Image=` 与它自己的段名不同时。**

真实例子 —— 盟军天气控制仪：

```ini
; rulesmd.ini
[GAWEAT]                 ; 这是「类型 ID」
Image=GAWETH             ; 而它用的是「GAWETH」这个 ART 段
```

```ini
; artmd.ini
[GAWETH]                 ; 外观与 Foundation 都写在这里（Foundation=3x3）
```

所以模仿它时要写两个键：

```ini
[NAMISL]
ShowByArt=GAWETH         ; 外观：段名
ShowByArtType=GAWEAT     ; 占地：类型 ID
```

**只写段名会怎样**：外观正常，但**占地不会跟随**（并且日志会提示找不到类型）。
这个不对称很容易误判，所以遇到"外观对了、占地没变"先检查这里。

### 完整示例

```ini
; ── 苏军建筑显示成盟军建筑 ──────────────────────────

[NACNST]                     ; 苏军建造厂 → 盟军建造厂
ShowByArt=GACNST

[NAPOWR]                     ; 苏军电厂 → 盟军电厂（占地 3x2 → 2x2）
ShowByArt=GAPOWR

[NAHAND]                     ; 苏军兵营 → 盟军兵营（占地 2x2 → 3x2）
ShowByArt=GAPILE

[NAREFN]                     ; 苏军矿厂 → 盟军矿厂
ShowByArt=GAREFN

[NAYARD]                     ; 苏军船厂 → 盟军船厂
ShowByArt=GAYARD

[NAMISL]                     ; 苏军核弹 → 盟军天气控制仪（段名≠类型 ID）
ShowByArt=GAWETH
ShowByArtType=GAWEAT
```

反过来做（盟军建筑显示成苏军）把两边的名字对调即可：

```ini
[GACNST]
ShowByArt=NACNST
```

### 生效时机

配置在**每局游戏开始、引擎解析建筑 ART 时**读取。

> ⚠️ **改完 ini 必须重启游戏**。而且由于引擎只在解析 ART 那一刻读段名，
> 运行中改 ini 不会生效（这是引擎的机制，不是本功能的选择）。

### 如何确认生效

看游戏目录下的 `karst.log`，正常会有这几行：

```
ShowByCountry[redirect]: scanned 402 type(s), 6 declare ShowByArt, 6 redirect entr(ies)
ShowByCountry[redirect]: NAPOWR -> art section 'GAPOWR'
ShowByCountry: 6 building(s) redirect their art (ShowByArt).
ShowByCountry[parse] NAPOWR: ART section set to 'GAPOWR' before the engine reads it.
ShowByCountry[foundation]: NAPOWR now uses GAPOWR's footprint: foundation 5->3 ...
```

| 日志 | 含义 |
| --- | --- |
| `scanned ... 0 declare ShowByArt` | 配置没读到 → 检查键名拼写、段名是否正确 |
| 有 `[redirect]` 行但没 `[parse]` 行 | 段名读到了，但引擎解析该建筑时没走到 → 报告给开发者 |
| `[foundation] ... skipped` | 占地没复制（通常是段名≠类型 ID 但没写 `ShowByArtType`） |
| 完全没有 `[redirect]` 行 | 一局里没有配置任何 `ShowByArt` |

### 已知边界

| 事项 | 说明 |
| --- | --- |
| **不支持按国家区分** | 这里只支持"某建筑的固定外观"（全局生效）。要按拥有者国家显示不同外观，用第三节的 `ShowByCountries` / `ShowBySHP`（那是另一套机制：每个国家一份类型副本），两者可同时使用 |
| 占地只跟随 `Foundation` | 其它规则（血量、造价、前提等）仍来自建筑自己的 rules 段，不会跟随 |
| 目标段必须存在 | `ShowByArt` 指向的段若不存在，引擎解析不到任何东西 → 建筑会失去外观 |
| 单位/步兵不适用 | 目前只处理建筑（`BuildingTypeClass`） |

## 二、Sidebar.MixFileIndex —— 让**每个国家**用不同的侧边栏

### 它做什么

指定某个**国家**使用哪个侧边栏界面（`SIDECnnMD.MIX`）：

```ini
[Americans]
Sidebar.MixFileIndex=2      ; 美国使用 sidec02.mix（苏军侧边栏）

[Russians]
Sidebar.MixFileIndex=1      ; 俄国使用 sidec01.mix（盟军侧边栏）
```

换了之后，**侧边栏的整个外观**（面板、按钮位置、雷达框、资金条）都变成那个 MIX 的样子 ——
全部由引擎自己加载和绘制，Karst 只负责"决定用哪一个"。

### 与 Ares 的区别（重要）

| | Ares 的 `Sidebar.MixFileIndex` | Karst 的 `Sidebar.MixFileIndex` |
| --- | --- | --- |
| 粒度 | **阵营**（Side） | **国家**（Country） |
| 配在哪 | `[阵营名]` 段，如 `[Fourthside]` | `[国家名]` 段，如 `[Americans]` |
| 同一阵营内不同国家 | ❌ 做不到（共用一个） | ✅ 可以各不相同 |

两者**可以同时使用**：Ares 先按阵营定一个，Karst 再按国家覆盖（仅当该国家配了这个键）。

### 编号规则

**1-based**，和 Ares 一致：

| 值 | 文件 |
| --- | --- |
| `1` | `SIDEC01MD.MIX` |
| `2` | `SIDEC02MD.MIX` |
| `3` | `SIDEC03MD.MIX` |
| … | … |

对应文件放在游戏目录即可（就是原版 `sidec01.mix` / `sidec02.mix` 那种文件）。

### 实用示例

```ini
; ── 让特定国家拥有自己的界面 ──────────────────────

[Americans]                  ; 美国 → 第三套界面
Sidebar.MixFileIndex=3

[YuriCountry]                ; 尤里 → 第一套
Sidebar.MixFileIndex=1

; 没有写这个键的国家，行为完全不变（不会被动到）
```

### 如何确认生效

`karst.log` 里会有：

```
ShowByCountry[mixcountry] 'Americans' (index 0) -> Sidebar.MixFileIndex=2
ShowByCountry[mixcountry] 'Russians' (index 8) -> Sidebar.MixFileIndex=1
```

- 有这行 → 配置被读到并应用了
- **没有**这行 → 该国家没配这个键（或配的值 < 1），引擎按原样处理

> 日志里的 `index N` 是引擎给出的国家索引，可以用来核对读到的到底是不是你想的那个国家。

### 生效时机

和原版一样，在**开始一局游戏时**（引擎加载侧边栏 MIX 的那一刻）。

> ⚠️ 改完 ini 要**重新开始一局**（退出到主菜单再进也行）。

### 已知边界

| 事项 | 说明 |
| --- | --- |
| 目标是**玩家自己**的界面 | 侧边栏只属于本机玩家，所以是按"玩家选择的国家"生效的；对手国家不影响你的界面 |
| 需要对应的 MIX 文件存在 | 指向不存在的 `sidecNN.mix`，侧边栏会加载不出来 |
| 值必须 ≥ 1 | 写 `0` 或负数视为"未配置"，不做任何改动 |
| 与 Ares 共存 | 两者 hook 的地址不同，不会冲突 |

## 三、CountryArt —— 按**拥有者国家**显示不同建筑外观

> 状态：**已实机验证通过**（2026-10-11）。同一进程内连续三局（美国 → 韩国 → 法国），
> 外观、占地、侧边栏图标全部正确，无崩溃（验收记录见本章末）。

### 它做什么

同一个建筑，按**拥有者的国家**显示成不同的图像（含活动件动画、占地、侧边栏图标）：

| GACNST 的拥有者 | 显示成 |
| --- | --- |
| `Americans`（美国） | `YACNST`（尤里建造厂） |
| `Alliance`（韩国） | `NACNST`（苏军建造厂） |
| 列表之外的国家 | 保持原样，完全不生效 |

判定依据是**拥有者国家**，人类玩家和电脑玩家一视同仁。
建筑的**身份不变**：它仍然是 `GACNST`（造价、血量、建造前提、名字都是盟军建造厂的），
只是画成了另一个 ART 段的样子。

### 配置方法

写在**建筑自己的段**里，两个**平行列表**（位置一一对应）：

```ini
[GACNST]
ShowByCountries=Americans,Alliance
ShowBySHP=YACNST,NACNST
```

| 键 | 必需 | 含义 |
| --- | --- | --- |
| `ShowByCountries` | ✅ | 国家名列表（必须与引擎的国家列表一致） |
| `ShowBySHP` | ✅ | ART 段名列表，与上一行**一一对应** |

位置：`rulesmd.ini`（优先）或 `artmd.ini`。别名：`art.show_by_countries` / `art.show_by_shp`。

| 下标 | ShowByCountries | ShowBySHP | 含义 |
| --- | --- | --- | --- |
| 0 | Americans | YACNST | 美国的 GACNST 显示成 YACNST |
| 1 | Alliance | NACNST | 韩国的 GACNST 显示成 NACNST |

### 校验规则（不满足就报错并忽略该条，不会半个映射悄悄生效）

| 情况 | 结果 |
| --- | --- |
| 只写了 `ShowByCountries` 或只写了 `ShowBySHP` | 报错、忽略 |
| 两个列表长度不一致 | 报错、忽略 |
| 国家名不在引擎的国家列表里 | 报错、忽略 |
| 同一个国家重复出现 | 报错、忽略 |
| 列表里有空项（多余的逗号，如 `Americans,,Alliance`） | 报错、忽略 |
| 键写了但值是空的（`ShowByCountries=`） | 视同没写；若两行都空，这条不生效也**不报错**（与上面几种不同） |

> 校验用的是**引擎自己的国家列表**（`HouseTypeClass::Array`），所以 mod 新增的国家同样有效；
> 国家名大小写不敏感，内部会归一成引擎的规范拼写。

### 批量配置

```powershell
python Karst\tools\countryart_config.py --show                    # 看当前配置
python Karst\tools\countryart_config.py --write GACNST            # 写一个建筑
python Karst\tools\countryart_config.py --write all               # 写脚本内置的 7 个建筑
python Karst\tools\countryart_config.py --remove                  # 把这 7 个建筑的键移除
python Karst\tools\countryart_config.py --show --file "D:\游戏\rulesmd.ini"   # 指定别的文件
```

注意事项（都是脚本的实际行为）：

* **默认目标是写死的** `E:\_game\RA2\yr_karst_test\rulesmd.ini`。换机器或用别的游戏目录，
  必须加 `--file "<路径>"`。
* 只认它内置的 7 个建筑（GACNST / GAREFN / GAPOWR / GAPILE / GAWEAP / GATECH / GAYARD，
  见脚本里的 `ART` 字典），写入的国家列表固定为 `Americans,Alliance`；
  要别的国家或别的建筑就手工改 ini。
* 写入位置是**该段标题行的正下方**，并会删掉该段内原有的同名键（避免一个段里两份）。
  **其它行一个字节都不动**，行尾（CRLF/LF）跟随文件本身。
* 每次写入前自动备份为 `<原文件>.bak-before-countryart-<时间戳>`。

### 它是怎么做到的（四条要点）

1. **必须按国家复制"类型对象"**：`ImageFile` 在 `BuildingTypeClass` 上，而同建筑的所有实例
   共用一个类型对象，所以"同建筑、不同国家、不同外观"只能每个 (建筑 × 国家) 建一份副本，
   再让建筑实例指向自己国家的那份。
2. **图像必须由引擎自己解析**：副本是源类型的拷贝，一开始带着源类型**已解析好的**动画名和
   SHP 指针；手工去改这些字段正是这个功能历史上被撤下的原因（"主体来自目标段、动画名还是
   源类型"，活动件错乱）。所以 Karst 只决定**用哪个段名**，随后让**引擎自己的 ART 解析器**
   去读那个段 —— 图像、活动件、Buildup、DeployingAnim 全部由引擎建立。
3. **副本每局重建**：引擎在新一局会重建建筑类型对象（实测同一个 GACNST 第一局
   `0x16A370D0`、第二局 `0x16E33040`），旧副本指向已经消失的局面。因此副本与它的源类型绑定，
   引擎一旦给出不同的对象就丢弃重建（generation N）。
4. **侧边栏图标要额外一步**：建造栏列出的是引擎类型数组里的**源类型**，副本不在数组里，
   所以图标在 `GetCameo` 入口按**本地玩家**国家换成副本 —— 玩家看到的图标与将要造出来的
   建筑一致。只有当副本**确实带图标**时才替换，否则保留原来的，免得玩家凭空少一条建造项。

引擎偏移、hook 地址与逐条实测依据见 [`二次开发须知.md`](二次开发须知.md) §4.9（维护者向）。

### 生效时机

分两件事，很容易搞错：

| 什么 | 什么时候读/做 |
| --- | --- |
| **配置**（`ShowByCountries` / `ShowBySHP`） | **进程内只读一次** —— 第一次解析建筑 ART 时。之后不再读 |
| **副本**（每个建筑 × 国家的类型对象） | **每局重建** —— 引擎换掉建筑类型对象时，副本跟着重做（`generation N`） |

所以：改完 ini 必须**重启游戏**（只退回主菜单再开一局**不够**）。不需要重新编译。

### 如何确认生效

`karst.log` 里**每次启动**（不是每局）会有一行配置摘要：

```
CountryArt: 7 building(s) declare ShowByCountries, 14 rule(s) in total.
```

然后**每局一行**：

```
CountryArt: generation 1 - 7 building(s), 14 rule(s) active, 0 rebuild(s) so far.
```

`generation` 每局加一（第 2 局是 `generation 2`），`rebuild(s)` 是累计重建次数。
把 `karst.ini` 的 `LogLevel` 设为 `debug`，还能看到
`CountryArt[parse]` / `[target]` / `[use]` / `[state]` / `[cameo]` / `[slots]` 等逐步细节。

### 排错

| 日志关键字 | 含义 |
| --- | --- |
| `CountryArt: N building(s) declare ShowByCountries, M rule(s)` | 配置读到了（**每次启动一行**；没这行 = 键名/位置不对，或引擎还没解析 ART） |
| `CountryArt: ... is ignored` | 某条配置被校验拒绝（原因写在同一条日志里） |
| `CountryArt: generation N - ...` | **每局一行**：第 N 代副本已就绪 |
| `CountryArt[parse]`, `[target]`, `[use]`, `[state]`, `[cameo]`, `[slots]` | debug 级过程细节 |

> 排错顺序：先确认有 `declare ShowByCountries` 那行（说明配置读到了），再确认 `generation`
> 那行（说明副本建好了），最后才怀疑外观/图标的细节。

配套工具：`countryart_config.py`（写 / 查 / 移除配置）、`hookcheck.py`（改 hook 后必跑）、
`hookconflict.py`（是否与 Ares/Phobos/Kratos 交叠）、`hooktable.py`（列出全部 hook）、
`disrva.py`（按 RVA 反汇编任意 DLL）。

### 已知边界

| 事项 | 说明 |
| --- | --- |
| **改 ini 必须重启游戏** | 配置在进程内只读一次；退回主菜单再开一局**不会**重读（见"生效时机"） |
| **读档后外观回原样** | 副本不加入引擎的类型数组，存档里记的是原类型；读档后建筑指回原类型。逻辑无误，只是外观回到原样 |
| 只在**构造时**判定一次 | 建成后被工程师占领换主，外观不会改变 |
| 目标段必须存在 | `ShowBySHP` 指向的 ART 段不存在 → 副本没有图像（引擎不会为此报错） |
| 侧边栏图标按**本地玩家**国家 | 侧边栏只属于本机玩家，对手国家的界面不受影响 |
| 与 `ShowByArt` 可共存 | 前者给每个国家独立副本，后者改共享类型的段名（全局），互不干扰 |
| 副本不释放 | 每规则每局约 6 KB，故意留着（上一局的建筑可能还指着它） |

### 实机验证记录（2026-10-11）

同一进程三局，配置 7 个建筑（GACNST / GAPOWR / GAREFN / GAPILE / GAWEAP / GATECH / GAYARD）：


无崩溃、无异常退出；占地跟随（`foundation 18->18` 等）与图标切换同时得到确认。

## 四、INI 热重载 —— 改完 ini 不用重启游戏

### 它做什么

游戏运行期间，保存**你指定的**规则 ini 文件，Karst 会立刻重读这些文件并把新的数据
灌回引擎的类型对象 —— 不用退出战斗、不用重开游戏。

```ini
; 游戏目录下 karst.hotreload.ini
[IniHotReload]
Enabled=yes
Files=rulesmd.ini,artmd.ini,aimd.ini
Types=BuildingType,UnitType,InfantryType,AircraftType,WeaponType,WarheadType,BulletType,AnimType,VoxelAnimType,ParticleType,ParticleSystemType,OverlayType,SmudgeType,SuperWeaponType,HouseType,Side
```

`Types=` 决定**哪些种类的类型会被重灌**（详见下方"类型白名单"）。当前默认值是
**除 `IsotileType` 外的全部 16 类**，已实机逐类验证。

### 类型白名单（Types=）

重灌一个类型 = 调用它自己的 `LoadFromINI` 再读一遍，那是"只为游戏启动期编写过"的
引擎/扩展代码。所以有一个白名单，让危险范围可控。

| 值 | 含义 |
| --- | --- |
| `default` | 只重灌**建筑**（最早验证过的那一档） |
| `all` | 除 `TerrainType` 外的全部 17 类 |
| `none` | 什么都不重灌（文件仍会被解析和报告） |
| `buildings` / `units` / `weapons` | 分组：建筑 / 单位·步兵·飞机 / 武器·弹头·子弹 |
| `WarheadType,AnimType` | 直接写类名，逗号分隔 |

**实测数据（本机，游戏内，逐类验证过）**：

| 配置 | 重灌类型数 | 耗时 | 结果 |
| --- | --- | --- | --- |
| `default` | 398 | 265 ms | 稳定 |
| `default,units` | 553 | 469 ms | 稳定 |
| `default,units,weapons` | 914 | 422 ms | 稳定 |
| `all` | 1792 | 484 ms | 稳定，但 1187 failed |
| 当前默认（16 类） | 1792 | 469 ms | 稳定，123 failed |

* **17 类实测都不会崩**；`TerrainType` 被代码直接拒绝（参考实现实测会崩）
* **耗时基本不随类型数增长**：开销主要在读约 1.2 MB INI 文本 + 重建小节快照（约 140 ms 基线）
* 默认值排除了 **`IsotileType`**：它有 1064 个成员、**没有一个能成功重灌**
  （没有 INI 小节，是引擎从等距瓦片内建的），只会把失败计数从 123 抬到 1187；
  排除后成功重灌数分毫未变
* 日志里的 `failed` 大多是**无害**的：某类型没有自己的 INI 小节时 `LoadFromINI` 会返回 false。
  在 INI 里搜 `[类型名]`，搜不到就是正常

要说明的两点：

* **分组是"追加"而不是"替换"**：`Types=weapons` 表示"默认的建筑 + 武器组"，
  只有 `all` / `none` / `default` 会重置集合。要精确集合请从 `none` 开始（如 `Types=none,units`）。
* **`TerrainType` 写了也会被拒绝**（参考实现实测会崩），日志里会说明。

改了 `Types=` 需要**重启游戏**才生效（它在启动时读一次）。

### 性能

一次重载只重灌**本次改动到的段**对应的类型，不是整表。实测（3446 个段里改 1 个）：

```
IniHotReload: 3446 section(s) seen, 1 changed: gapowr(changed)
IniHotReload: 3 file(s) read, 1 type(s) refed, 0 failed, 401 skipped out of 3631 in 139.9 ms.
```

进程内的**第一次**重载没有基线可比，会全表重灌一次（约 470 ms（见上表））建立基线，之后就是上面
这种增量。把 `Files=` 列表收短也能减少每次的耗时。

### 这一份列表就是功能的全部边界

**只有 `Files=` 里列出的文件会被监视和重读。** 没列出的文件（包括 `RA2MD.INI`、
`karst.ini`、`ddraw.ini`、`soundmd.ini`）完全不碰 —— 你改它们，Karst 不会有任何反应。

| 规则 | 说明 |
| --- | --- |
| 只接受 `.ini` | 后缀**写死在程序里**，不能配置。写 `rules.txt` 会被记日志并忽略 |
| 文件必须存在 | 不存在的条目被忽略（不会监视一个不存在的路径） |
| 必须在游戏目录内 | 绝对路径指向别处会被拒绝，防止误改其它安装 |
| 按列表顺序重读 | 读 ini 是**合并**，所以后面的文件覆盖前面的；当前地图在最后读（与引擎一致） |
| 列表为空 / `Enabled=no` | 功能不启用（默认配置就是启用，删掉文件即关闭） |

条目被拒绝不会导致半个生效：被拒绝的条目单独忽略，其余照常工作，原因写在日志里。

### 什么时候生效、什么时候不生效

改动会在**下一次保存后约 1.5 秒**、且在游戏跑到帧边界时应用（去抖是为了避免读到
编辑器还没写完的半个文件）。生效范围：

| 会立即生效 | 不会生效 |
| --- | --- |
| 类型对象上、从 INI 读出来的字段（本版本：**建筑类型**相关） | 全局标量段，如 `[General]`（本版本不重读） |
| 新造出来的单位/建筑（它们用新值） | **已经建好的**实例：构造时复制到实例上的字段保持旧值 |
| 多个文件同时保存（一次重载全部处理） | `TerrainType`：**永不重读**（参考实现实测会崩） |

### 生效时机

保存文件即可，**不需要重启游戏、不需要重新开始一局**。改完想确认的话看日志。

### 如何确认生效

`karst.ini` 里 `LogLevel=debug`、`DebugLog=yes` 时，`karst.log` 会先后出现：

```
IniHotReload: 3 file(s) watched: rulesmd.ini,artmd.ini,aimd.ini
IniHotReload: watching E:\_game\RA2\yr_karst_test\ for changes.
IniHotReload: 'rulesmd.ini' changed, reloading.
IniHotReload: 4 file(s) read, 37 type(s) refed (0 failed, 1420 skipped out of 1457) in 12.3 ms.
```

* `watched` / `watching` 各一行 —— 启动时就绪。
* `changed, reloading` —— 检测到你保存了哪个文件。
* 最后一行是**结果**：读了几份文件、重灌了多少个类型、失败与跳过数、耗时。
* 超过 50 ms 会附一句提示（列表太长可以缩短）。

都没看到时，先确认：文件真的存在于游戏目录、`karst.hotreload.ini` 的 `Files=` 里有它、
条目没有被日志里的 `is ignored` 拒绝。

### 已知边界

| 事项 | 说明 |
| --- | --- |
| `[General]` 等全局标量不重读 | 本版本只重灌类型对象；这类改动仍需重新开始一局 |
| 已建实例不跟随 | 造价/血量等若在建造时被复制到实例上，实例保持旧值（新建的用新值） |
| 只有建筑类型 | 其它类型（单位/武器/弹头…）本版本**刻意跳过**，等建筑验证稳定后再逐类放开 |
| `TerrainType` 永不重读 | 参考实现注明会崩，不冒险 |
| 与 Karst 自己两个功能的关系 | `ShowByArt` 是**每次 ART 解析时**读的（不缓存），所以在重载后**新**触发的 ART 解析能看到新值；`ShowByCountries`/`ShowBySHP` 的**类型副本**在每局第一次 ART 解析时建立，重载**不会重建**它们 —— 改这两类配置仍建议重新开始一局 |
| 只影响本次运行 | 不写回文件、不进入存档；新开一局本来就会重新读盘 |
| 建议不要在重载后于同一局内存档 | 存档里的类型状态与磁盘 ini 可能不再对应 |
| 联机场景不要用 | 没有哈希同步机制，仅适合单机/调试 |

## 五、脚本（JSON 外观脚本）—— **已移除**

`karst.scripts.ini` + `Karst\scripts\*.jsonc` 这套"用 JSON 描述建筑外观"的机制已经删除，
相关源码、配置示例与配套的 `script-editor.html` 编辑器一并移除。

* **长期无人维护** —— 相关源码自首次推送以来没有一次改动，也没有扩展出第二种脚本类型。
* **从未实际启用** —— 测试环境里 `Karst\scripts` 目录一直不存在，日志固定为
  `Scripts: script directory ... does not exist; scripts off.`。
* **已被 C# 脚本覆盖** —— 需要"不写 C++ 的扩展能力"时，用 `dyrinpr\` 的 C# 脚本系统（第三部分），
  能力更强且仍在维护。

## 六、BuildCost —— 一条规则统一所有造价

> 状态：**已实机验证通过**（2026-10-16）。
> 构建期 `hookcheck` / `hookconflict` 通过（12 个 hook 全部合规、与 Ares/Phobos/Kratos 无重叠）；
> 游戏内实测 `karst.log`：553 个类型段被定价为 800，游戏正常运行至进入地图、无崩溃；
> 侧边栏里所有单位/建筑的显示价格实测均为 800。

### 它做什么

在 `rulesmd.ini` 的 `[General]` 段写一个整数，**所有**单位、步兵、飞机、建筑的造价都变成这个值：

```ini
[General]
BuildCost=800
```

于是灰熊坦克、步兵、光棱塔……在价格上完全平等：侧边栏显示 800，建造时扣 800，取消时按 800 退款，
AI 的估价也按 800。

**不写这个键就什么都不发生**：功能对引擎状态的写入为零，与没装 Karst 时逐字节一致。

### 建造时间也会跟着变（这是引擎自己的公式）

`gamemd.exe` 1.001 里建造时间的算法是（反汇编实测）：

```
建造帧数 = (int)(Cost × RulesClass::BuildSpeed × 0.9)
```

被 `BuildCost` 改掉的正是这个 `Cost`（`TechnoTypeClass+0x610`），所以 `BuildSpeed=.7` 配
`BuildCost=800` 时，所有东西都是 `800 × 0.7 × 0.9 = 504` 帧 ≈ 33.6 秒。
这不是 Karst 另外做的事，而是引擎本来的算法 —— 造价变了，由造价推出来的时间自然跟着变。

如果你要的是"只改花钱、不改时间"，那是另一套做法（需要在造价查询路径上另开挂点，
并且 `Cost` 字段本身不能再动），目前**没有**实现。

### 生效范围

| 会变 | 不会变 |
| --- | --- |
| 侧边栏显示的价格、建造扣款、取消退款 | 单位/建筑的其他属性（血量、火力、速度、视野……） |
| AI 的造价评估 | `rulesmd.ini` 里 `Cost=` 的原值（文件不动，只是读进来时被替换） |
| 建造时间（原因见上） | 超武、弹头、动画、抛射体、地形等**没有造价字段**的类型 |

`BuildCost=0` 是合法值（全部免费）。负值被忽略并只在日志里警告一次。

### 实现方式（引擎事实）

字符串 `"Cost"` 在整个 `gamemd.exe` 里**只有一处**读取会写进类型的造价字段，而步兵 / 车辆 /
飞机 / 建筑**全都汇到这一处**，所以一个 hook 就够：

```
0x0071469F  mov  ecx, [ebp + 0x610]   ; 类型的当前 Cost，作为默认值
0x007146A5  push ecx
0x007146A6  push 0x825470             ; "Cost"
0x007146AB  push ebx                  ; 段名（就是类型 ID）
0x007146AC  mov  ecx, esi             ; CCINIClass*（规则 INI）
0x007146AE  call 0x5276D0             ; CCINIClass::ReadInteger
0x007146B3  mov  [ebp + 0x610], eax   ; ← Karst 在这里挂钩（6 字节）
```

Karst 在**引擎写入之前**把 `[General] BuildCost` 的值放进 `EAX`，于是写出这个值的仍然是引擎
自己那条指令 —— 结果和"INI 里真写了 `Cost=800`"没有区别，不需要事后遍历类型数组。

值是从**引擎当时正在读的那个 INI 对象**（`ESI`）里读的，而不是从 `CCINIClass::INI_Rules`
单例读，这样热重载（第四节）用临时 INI 重灌类型时读到的是新值。

因为挂在"读 INI"这一步，**改了 `rulesmd.ini` 再触发热重载，造价会自动重新应用**。

### 如何确认生效

`karst.log`（需 `karst.ini` 里 `LogLevel=debug` 或 `info`）：

```
BuildCost: watching [General] BuildCost in the rules INI.
BuildCost: [General] BuildCost=800 - every TechnoType's Cost is now this value.
BuildCost: first type priced from section 'GACNST'.
BuildCost: <类型总数> type section(s) priced at 800.
```

（2026-10-16 在 `yr_karst_test` 实测：段名是 `GAPOWR`，总数 553，全程无崩溃。）

* 有第 1 行、没有第 2 行 → `[General]` 里没读到这个键：检查段名、键名拼写、以及它是否被
  写在了别的小节下面。
* 有第 2、3 行 → 挂钩点正确（第 3 行会打印真实读到的类型段名）。
* 最后一行是累计条数，数量取决于你的规则文件里有多少个类型，每次有变化才打印一次。

### 已知边界

* 只改**造价**这一个字段；如果你期望"价格统一但建造时间按原价算"，目前不支持（见上）。
* 有些类型本来靠 `Cost=0` 表达特殊语义（假建筑、装饰物等），统一之后它们也会被标价 ——
  这正是"所有类型统一"的字面含义。
* 值很大时建造时间会同步变长（`Cost × BuildSpeed × 0.9`），不是 bug。

## 七、VirtualSeat —— 让载具拥有"看不见的载员"

### 它做什么

给一辆载具（或飞机）凭空加几个**看不见的乘客**，让它们像真实乘客一样**自动索敌、开火**，
而且每个座位可以有自己的枪口位置。

和"给载具加一门武器"的区别：这里的每一个虚拟座位都是一个**真实存在的隐藏单位**，
索敌、装填（ROF）、弹药、精英武器、开火动画全部由引擎自己负责——不是模拟出来的效果。

### 配置方法

两步，缺一不可。

**第一步：`rulesmd.ini` 里写座位表**

```ini
[BFRT]
VirtualSeat=LUNR,GGI,SHK,FV,DESO
```

* 逗号分隔，**按顺序**对应枪口 0、1、2…
* 只接受**步兵 / 载具 / 飞机**。写建筑（如 `GAPOWR`）会被拒绝并 `[ERROR]`，
  该类型**一个座位都不会创建**
* 最多 **5** 个——引擎只有 5 个乘客开火位（原因见下）

**第二步：`artmd.ini` 里写枪口**

```ini
[BFRT]
VirtualFLH0=0,0,100
VirtualFLH1=0,0,200
VirtualFLH2=0,0,300
VirtualFLH3=0,0,400
VirtualFLH4=0,0,500
```

* 每个值是 `X,Y,Z`，**相对于载具**的偏移（和 `AlternateFLH` 同样的量法）
* 座位数与枪口数不一致只会**警告**，不影响功能：多出的座位从载具**中心**开火

### 为什么不复用 AlternateFLH（重要）

`AlternateFLH0..4` 是**整辆车共享的公共资源**。引擎按乘客在载具乘客链表里的**顺序**分配，
第 i 个乘客拿 `AlternateFLH{i-1}`；而且**只认到第 5 个**，第 6 个开始退化成 `(0,0,0)`
——也就是从车体中心开火，**既不报错也不会不开火**，极难察觉。

所以虚拟座位如果去抢这套枪口：

| 车上真实乘客 | 结果 |
| --- | --- |
| 0 个 | 虚拟座位占用 `AlternateFLH0..4` ✅ |
| 2 个 | 真实乘客占 0/1，虚拟座位只剩 2/3/4，第 6 个起从中心开火 ❌ |
| 5 个 | 虚拟座位**一个枪口都没有** ❌ |

`VirtualFLH` 正是为避开这件事而独立出来的。两者互不干扰：真实乘客照旧用 `AlternateFLH`，
虚拟座位只用 `VirtualFLH`。

### 生效时机

* 座位在**载具出现在地图上**时创建（建造完成、运输机空投、读档还原都算）
* 改完 `VirtualSeat=` 需要**新造一辆**才生效；已经造出来的载具不会重建座位
* `artmd.ini` 的 `VirtualFLH` 是**启动时读一次**，改完要重启游戏

### 如何确认生效

`karst.log` 里每个座位一行，并带上它拿到的枪口：

```
VirtualSeat: [BFRT] -> 5 seat(s) resolved: LUNR, GGI, SHK, FV, DESO
VirtualSeat: [BFRT] 5 seat(s) match 5 gun port(s) in ART section 'BFRT'.
VirtualSeat: seat 0 on carrier 2E2EE3C0 <- created 'LUNR' (2DE2ACE8), port (0,0,100).
VirtualSeat: 1 carrier(s) populated, 5 seat object(s) created.
```

**最直观的验证是枪口差异**：把 `VirtualFLH` 的 Z 写成明显不同的值（如 100/200/300），
生效时子弹会从**车体正上方不同高度**射出。

### 已知边界

* 最多 5 个座位（引擎限制）
* 虚拟座位**不占** `Passengers=` 的容量，载具仍可正常装载真实乘客
* **载具被摧毁时虚拟座位一起消失**，不会掉成免费单位
* 座位类型避免**时空武器**（原版 `OpenTopped` + 时空本就是有 bug 的区域）
* 存档会带上这些隐藏单位；读档后不会重复创建

## 八、DistributeBuild —— 每个建筑提供一次超级武器

> 状态：**已实机验证通过**（2026-11-03）：3 个铁幕装置 → 图标显示 3 份可用，连放 3 次后变暗，
> 各建筑独立冷却、冷却好一份就恢复一份。

### 它做什么

原版里一个超级武器对每个玩家只有**一份**充能：造出第一个铁幕装置时引擎授予这份充能，
之后再造多少个同样的建筑都不会多。`DistributeBuild=yes` 让**每个**带有该超级武器的建筑
各提供一份、并且**各自独立充能**。

```ini
[IronCurtainSpecial]
DistributeBuild=yes
```

- 写在**超级武器类型段**（`[XXXSpecial]`），不是建筑段。
- 建筑只要通过 `SuperWeapon=`、`SuperWeapon2=` 或 `SuperWeapons=`（逗号列表）指向该超级武器
  即可，**不需要新的建筑标签**；这三种写法都支持。
- 没写这个键的超级武器行为**完全不变**，原有标签的语义也不变。

### 界面上怎么表现

侧边栏仍然只有一个图标（引擎每个类型只有一个充能对象，这一点没有改）：

- 只要还有**任意一个**建筑的那份充能是满的，图标就是"可用"；
- 每按一次，消耗其中**最早充满**的那一份，那一份随即按 `RechargeTime=` 重新充能；
- 图标上的进度条表示"距离下一份可用还有多久"；
- 全部用完时图标变暗，直到下一份充满。

**可用次数提示**：每次份数变化时，游戏消息区会打印一行（只有本机玩家能看到自己的）：

```
IronCurtainSpecial  3 / 3     ← 建筑数 3，三份都冷却好了
IronCurtainSpecial  2 / 3     ← 释放一次后
```

前半是超级武器类型 ID，后半是"当前可用 / 建筑总数"。冷却完成一份 +1，释放一次 -1。

### 生效时机与排查

- 建筑**建好那一刻**开始充能；卖掉或摧毁时，它那份充能（无论用没用过）一起消失。
- 建造中的建筑（`InLimbo`）不计入。
- `karst.log` 里会出现一次 `DistributeSW: '<类型ID>' has DistributeBuild=yes ...`，
  以及 `DistributeSW: '<类型ID>' is in use - N building(s) provide it.`，用 N 确认建筑数被数对。
- 测试时可以把该超级武器段的 `RechargeTime` 临时改小（例如 `RechargeTime=300`），几秒就能看到
  多份充能依次完成；测完记得改回去。
- 如果写在了建筑段而不是超级武器段，功能**不会生效**，日志里也不会有上面的行。

### 已知边界

- 每帧遍历一次建筑列表维护充能表；建筑很多时有很小的固定开销（几百个建筑量级可忽略）。
- 载入存档后所有建筑从"刚开始充能"重新计算——引擎存档里没有"每建筑充能"这个概念，
  这是本功能自己维护的状态。
- 引擎自身的"充能完成"播报仍按它自己的单份计时器触发，可能与消息区里的份数不完全同步；
  可用性以图标和消息区的份数为准。

### 实现备忘（维护者）

- **不加任何 hook**。实测 Ares 与 Phobos 同时占用 `SuperClass::Launch`（`0x6CC390`，各 6 字节）
  和 `SuperClass::ClickFire`（`0x6CB920`，Ares 5 字节），挂在它们之后的钩子**运行时从不执行**
  （日志里充能正常、发射零回调）。因此"发射"改为从引擎状态推断：本模块每帧把
  `IsCharged` 置真，引擎/Ares 真正消耗时必然清假，观察到"我置真 → 变假"即扣一份。
- 建筑类型读 `BuildingClass::Type` 用**显式偏移 `+0x520`**（见 `src\Ext\EngineLayout.h`），
  不用 YRpp 成员：实测该成员偏移在此 build 上不可靠。
- 所属玩家：`TechnoClass::Owner`（`+0x108`）实测读到 `0`/`1`，不可信；改为在对象头
  `0x0..0x600` 内搜索"`HouseClass::Array` 里的真对象"，本机稳定命中 **`+0x14C`**。
- 超级武器归属从**规则 INI 按段名解析**（`SuperWeapon=` / `SuperWeapon2=` / `SuperWeapons=`），
  同样绕开结构偏移。

## 八之二、Cinematic —— 过场动画时鼠标仍然可用

### 它做什么

任务开场动画、地图触发的过场，正常会让引擎**锁住输入并藏起鼠标指针**：这段时间你既看不到
指针，也点不动任何东西。打开这个功能后，过场**照常播放**（黑边、剧情推进、脚本都不变），
但**鼠标保持可用**。

### 配置

```ini
; 游戏目录下 karst.ini
[Cinematic]
KeepMouse=yes
```

`no` = 恢复引擎原本的行为。

### 它到底改了什么（一句话）

引擎的 `LockInput` 触发动作会置两个东西：一个"这是过场"的场景标志（`Scenario+0x35A2`），
和一个"输入被锁"的标志（`0xA8ED9C`）。本功能**只在过场期间**把后者清回 0，并重新显示一次
指针；**不动**前者，也不动引擎的锁计数（`Scenario+0x62C`），所以 `UnlockInput`、黑边、
剧情触发全部按原样工作。

### 如何确认生效

`karst.log` 里，每次进入被锁状态会出现一行（每个进程最多 8 行）：

```
Cinematic: input was locked for a cinematic - the mouse is kept alive.
```

没有这行 = 这段时间引擎没有锁输入（比如普通遭遇战里根本不会触发）。

### 已知边界

| 事项 | 说明 |
| --- | --- |
| 只解除"输入锁"与"藏指针" | 过场照常播放；想跳过过场仍要靠游戏本身的跳过方式 |
| 只在本机生效 | 只影响操作者自己 |
| 与 Ares/Phobos 共存 | 不新增任何 hook，只是在主循环里改两个字节 |

## Karst 脚本编写指南（C#）

> 本文面向**想用脚本实现功能、但不想写 C++** 的人。
> 你不必懂引擎内部，照着示例改即可。

## 一、先跑通一个脚本（5 分钟）

### 1. 目录

```
<游戏目录>\
    Karst.dll
    dyrinpr\            ← 脚本系统的家
        Dyrinpr.dll     ┐
        KarstYRpp.dll        ├ 三个核心程序集（已随 Karst 一起分发）
        KarstExtension.dll   ┘
        compiler.config.json   编译配置（首次运行自动生成）
        Scripts\             ← 你的 .cs 脚本放这里
```

### 2. 常用 using 速查（写脚本先抄这组）

```csharp
using System;
using Dyrinpr;            // Logger
using Extension.Ext;             // TechnoExt / BulletExt
using Extension.Script;          // TechnoScriptable / BulletScriptable
using Extension.Utilities;       // ExtensionReference（保存"另一个对象"的引用）
using PatcherYRpp;               // Pointer<T>、CoordStruct、各种引擎类
using PatcherYRpp.Utilities;     // MathEx（随机数等）
```

> 少一个 `using` 是最常见的编译错误来源。特别是 **`ExtensionReference`** 和 **`MathEx`**
> 分别属于 `Extension.Utilities` 与 `PatcherYRpp.Utilities`，不在常用的那两个命名空间里。

### 3. 写第一个脚本

在 `dyrinpr\Scripts\` 下新建 `MyFirst.cs`：

```csharp
using System;
using Dyrinpr;          // Logger
using Extension.Ext;           // TechnoExt
using Extension.Script;        // TechnoScriptable
using PatcherYRpp;             // Pointer、CoordStruct 等

namespace Scripts               // 命名空间随便起，类名才是关键
{
    public class MyFirst : TechnoScriptable
    {
        public MyFirst(TechnoExt owner) : base(owner) { }

        public override void OnUpdate()
        {
            Logger.Log("MyFirst is running!");
        }
    }
}
```

### 4. 把它绑到一个单位

在 `rulesmd.ini` 里给目标单位加一行 `Scripts=`，值是**类名**：

```ini
[MTNK]                ; 灰熊坦克
Scripts=MyFirst
```

### 5. 进游戏

造一辆灰熊坦克。日志（`dyrinpr\dyrinpr.log`）会开始刷 `MyFirst is running!`。

**改完脚本不用重启游戏**——脚本宿主会自己监视 `dyrinpr\` 目录并重新编译。
但 `rulesmd.ini` 里改 `Scripts=` 需要重开一局。

## 二、能挂什么事件

在脚本类里覆写这些方法即可。**它们都由 Karst 自动驱动**，不需要你挂钩子。

| 方法 | 什么时候触发 |
| --- | --- |
| `OnUpdate()` | **每一帧**（做持续效果、计时、追踪） |
| `OnFire(Pointer<AbstractClass> pTarget, int weaponIndex)` | 该单位**开火**时 |
| `OnReceiveDamage(Pointer<int> pDamage, int DistanceFromEpicenter, Pointer<WarheadTypeClass> pWH, Pointer<ObjectClass> pAttacker, bool IgnoreDefenses, bool PreventPassengerEscape, Pointer<HouseClass> pAttackingHouse)` | 该单位**受伤**时 |
| `OnPut(CoordStruct coord, Direction faceDir)` | 该单位**出现在世界上**（第一次被驱动的帧） |
| `OnRemove()` | 该单位**被移除**时 |

> 目前**只有单位脚本**（`TechnoScriptable`）。子弹脚本基类 `BulletScriptable`
> 的 `OnDetonate` 驱动也已实现，但绑定方式尚未验证。

## 四、完整示例：开火后给目标下"追踪弹雨"

```csharp
using System;
using Dyrinpr;
using Extension.Ext;
using Extension.Script;
using Extension.Utilities;        // ExtensionReference
using PatcherYRpp;
using PatcherYRpp.Utilities;     // MathEx

namespace Scripts
{
    // 挂在单位上的脚本：开火时记录目标
    public class MissileRain : TechnoScriptable
    {
        public MissileRain(TechnoExt owner) : base(owner) { }

        private ExtensionReference<TechnoExt> _target = new ExtensionReference<TechnoExt>();

        public override void OnFire(Pointer<AbstractClass> pTarget, int weaponIndex)
        {
            if (_target.Get() != null)
                return;

            if (pTarget.CastToTechno(out Pointer<TechnoClass> pTechno))
                _target.Set(TechnoExt.ExtMap.Find(pTechno));
        }

        public override void OnUpdate()
        {
            TechnoExt target = _target.Get();
            if (target == null) return;

            CoordStruct pos = target.OwnerObject.Ref.Base.Base.GetCoords();
            int r = MathEx.Random.Next(-600, 600);

            Pointer<WeaponTypeClass> pWeapon = WeaponTypeClass.ABSTRACTTYPE_ARRAY.Find("RedEye2");
            Pointer<WarheadTypeClass> pWarhead = WarheadTypeClass.ABSTRACTTYPE_ARRAY.Find("BlimpHE");

            if (pWeapon.IsNull || pWarhead.IsNull) return;

            Pointer<BulletClass> pBullet = pWeapon.Ref.Projectile.Ref.CreateBullet(
                Owner.OwnerObject.Convert<AbstractClass>(),
                Owner.OwnerObject, 10, pWarhead, 100, false);

            if (!pBullet.IsNull)
            {
                pBullet.Ref.MoveTo(
                    pos + new CoordStruct(r, r, 2000),
                    new BulletVelocity(0, 0, 0));
            }
        }
    }
}
```

绑定：`[MTNK] Scripts=MissileRain`

效果：灰熊坦克开火后，目标头顶会不断落下小范围爆炸。

| --- | --- |
| 脚本没反应 | `dyrinpr.log` 里有没有 `compile file succeed!`；`in class Scripts.你的类名` 说明类被扫到了 |
| 编译错误 | `dyrinpr.log` 里的 `error CS....`，带文件与行号；改完自动重编 |
| 游戏崩溃 | `syringe.log` 里的 `Code: 0xC0000005 at 0x...` |
| 什么日志都没有 | 确认脚本放在 `dyrinpr\Scripts\`（子目录也可以，会递归扫描） |
| 改了 `Scripts=` 没生效 | `rulesmd.ini` 的改动需要**重开一局** |

**两个容易踩的点**：

1. **类名必须与 `Scripts=` 的值完全一致**（大小写敏感）。`Scripts=Disk` 对应
   `public class Disk`。
2. **编译失败的脚本会留下一个 0 字节 DLL**，随后加载时报
   `BadImageFormatException`——这**不是**你新脚本的问题，是它前面那个脚本没编过。
   按 `dyrinpr.log` 里的 `error CS...` 修掉即可。

## 八、不想写代码？用「脚本工作室」搭积木

手写 `.cs` 要自己记事件签名和 `using` 列表。**脚本工作室**把这些变成点选：
点积木，代码自动出现。

### 1. 打开

```
Karst\tools\script-studio\KarstScriptStudio.html
```

🔴 **一定要用独立浏览器窗口打开**（双击这个文件，或拖进 Edge / Chrome 窗口）。
在 IDE / 编辑器的**内嵌预览面板**里打开会被浏览器额外套一层沙箱，
"选择脚本目录""下载""复制"都会被拒绝 —— 这不是页面坏了，换个窗口就好。

### 2. 三步搭出一个能跑的脚本

1. 右上角 **选择脚本目录…** → 选 `<游戏目录>\dyrinpr\Scripts`
   （只需选一次；浏览器重启后要点一下"重新授权"）
2. 左边 **事件** 里点一个（比如「每帧 OnUpdate」），再点 **条件** 和 **动作**
   - 条件：`每 N 帧`、`概率 N%`、`自己血量低于 N%`、`自己的类型是…`、`目标是单位/建筑`…
   - 动作：`打日志`、`修改自己的血量`、`修改即将受到的伤害`、`在自己位置造成范围伤害`、
     `向目标发射武器`、`记住目标` / `打击记住的目标`…
   - 积木只加进**当前选中**的事件卡（点卡片标题切换），卡片里能用 ↑↓ 调顺序
3. 右边实时显示生成的 C#，点 **保存到脚本目录**

保存后**不用重启游戏**：Karst 会自动重编译它。去 `dyrinpr\dyrinpr.log` 找
`compile file succeed!`；有错会看到 `error CS....`。

### 3. 让它生效

跟手写脚本一样，在 `rulesmd.ini` 里给目标单位加一行（**值是类名，大小写敏感**）：

```ini
[MTNK]
Scripts=你在页面上填的类名
```

页面右下角会把这两行直接生成好给你复制。改 `rulesmd.ini` 要**重开一局**才生效。

### 4. 之后还能改

工作室生成的脚本，文件开头带一行机器可读的积木数据（是注释，不影响编译）：

```csharp
// @karst-studio {"v":1,"cls":"MyScript","events":[...]}
```

所以下次在「这个目录里的脚本」里点 **打开**，它会**还原成你当初的积木**，
而不是丢给你一大段代码。删掉这一行脚本照样能编译，但就只能当代码看了。

同一个列表里还能 **停用**（改名成 `.cs.pro`，Karst 不再编译它）、**启用**、**删除**。

### 5. 它相对手写脚本的好处

| | 手写 `.cs` | 脚本工作室 |
| --- | --- | --- |
| 事件签名 / `using` 列表 | 自己记，容易漏 | 自动生成 |
| 逻辑 | 全部自己写 | **搭积木生成完整逻辑** |
| 脚本管理（列出/再编辑/删除/停用） | 手工改名/删除 | ✅ 直连 `Scripts` 目录 |

### 6. 想扩展积木库

积木库和代码生成器都在 `Karst\tools\script-studio\blocks\*.js`，
每个积木就是一段带参数的 C# 模板。加完积木后跑：

```powershell

node Karst\tools\script-studio\tests\run_tests.js --compile
node Karst\tools\script-studio\tests\check_page.js
```

测试会**自动为每个积木生成一个 .cs 并用与游戏内相同的编译器编译**，
所以"这个积木能不能编译"不需要靠人肉去游戏里试。
细节见 `Karst\tools\script-studio\README.md`。

  * `deep_conditions` —— 三层条件嵌套 + 范围伤害
  * `target_filter` —— 条件是单位（提供 `out` 变量）→ 后续动作使用

### 2.2 这套夹具抓到的真 bug（都是"页面显示绿色、游戏里编译不过"的那类）

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | 大量 `error CS0103: 名称"self"不存在` | 代码生成是**单遍**：先写方法开头的声明、再问积木要代码，导致"需要 self"是事后才知道的。改为**两遍**（先扫描 needs，再生成） |
| 2 | `error CS0103: 名称"pTarget"不存在` | `向目标发射武器` 的事件白名单里写了 `OnUpdate`，但它的代码直接用 `pTarget`。白名单与 `needs` 判断必须**同时**满足 |
| 3 | `error CS0128: 已定义名为 hp_e1 的局部变量` | 积木生成的局部变量名用了**事件** id 而不是**积木** id，同一事件放两个同类积木就撞名 |
| 4 | `error CS0103: 名称"_rememberedTarget"不存在` | `记住目标` 写这个字段，但 `needs` 里没声明它，字段声明就没被生成 |
| 5 | 校验器把合法文档误判为错误 | 事件定义是按 id 做键的，对象里**没有** `id` 字段；校验器读 `edef.id` 得到 undefined，导致所有"限定事件"的积木都被判为放错位置 |

第 5 条特别值得记：它让校验器**误报**，比漏报更糟（用户会不信任它）。

   目录读写代码路径就绪 + 非铬系浏览器降级提示"。底层 API 的可用性此前已在
   `fs-probe.html` 上逐项实测通过（当时的实测记录随 HANDOFF 文档一并移出仓库）。
2. **积木覆盖范围**：当前是"标准范围"（日志 / 数值 / 伤害与爆炸 / 计时与概率 /
   目标引用）。激光、动画、超武、单位移动与变形、装饰器状态、子弹脚本**尚未实现**
   —— 目标是全量，按批次扩展，每批都要过 §2 的编译验收。
3. **降级路径**（Firefox/Safari 无 File System Access）：只做了能力检测与提示，
   未在真机上跑过整条"下载 `.cs` → 手动放进目录"的流程。
4. **子弹脚本**（`BulletScriptable`）：基类与 `OnDetonate` 驱动在源码里存在，但
   **绑定方式本身还没被验证过**，所以工作室目前只做单位脚本。

```powershell
# 构建
```

> `.ps1`，无 BOM 时中文会被解成乱码并报出与中文毫无关系的语法错误）。
